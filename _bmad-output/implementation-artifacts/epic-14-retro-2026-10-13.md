## Findings

Dispositions: **fix** = action item, **defer** = tracked elsewhere, **accept** = recorded so later retros stop re-flagging.

### F1. Nine migrations, none ever run against Postgres (fix, high)

Migrations 033 to 041 were written across the epic, and every story deferred "never run against a database" because none was available or authorized in the build (`deferred-work.md:48-52`, `:76`, `:80`, `:87`, `:91`, `:95`, `:108`; spec 14.6 Implementation Notes). All service tests mock `getClient`. Specific risks on record:
- 037 copies and then **drops** `checklist_comments` and `logistics_comments` (`deferred-work.md:91`).
- 036 and 039 drop CHECK constraints by name or pattern match (`deferred-work.md:87`, `:108`).
- 040 adds `groups.default_event_type`, and the group queries select it. Deploying code before 040 breaks every group read and write (`deferred-work.md:80`).

Prevention: epics that ship migrations need a "migration smoke against a real Postgres" step in the definition of done. Nobody authorized one during any build.

### F2. Unauthenticated item-comment GET exposed commenter emails (fixed; residual defer, medium)

The shared GET handler written in 14.2 (`lib/api/itemCommentHandlers.ts:41`, "no auth required, mirrors the event-comments GET") returned `u.email` from `getItemComments` (`lib/db/queries.ts`). It was copied from the older event-comments pattern, passed the 14.2 review, and surfaced only in the 14.3 review. Fixed by `cf7abe5` for all four item types. **Residual:** event comments (`components/groups/EventCommentSection.tsx:245`, `lib/services/eventService.ts:1181`) and wishlist comments (`lib/db/queries.ts:936`) still return creator email. Logged in `deferred-work.md` under `spec-item-comment-email-exposure`.

Prevention: specs that add or generalize an unauthenticated GET should state what fields it may expose.

### F3. Full test suite is red at baseline and at HEAD, with three timing-sensitive suites (fix, medium)

Full `jest` run today: baseline `ebc16cc^` had 71 failed suites (423 failed tests of 3,746); HEAD has 72 (430 of 4,017). The only suite-level differences are `EventPolls.test.tsx`, `EventTimeline.test.tsx` and `ItemCommentPopover.test.tsx` failing at HEAD, and `ChecklistCommentPopover.test.tsx` plus `publicPlanningService.test.ts` failing at the baseline only. The three that fail at HEAD pass 40 of 40 when run on their own, so they are load-sensitive (the same popover test fails under parallel runs at the baseline). `tsc --noEmit` reports 706 errors at HEAD, unchanged from the figure recorded in spec 14.3's Verification. Consequence: no story could rely on a green full suite; each story verified a targeted subset.

### F4. Spec and PRD/architecture were not reconciled with the epic (fix, medium; spec reconciliation)

`epics.md:324` says FR79 to FR84 are "pending addition to the PRD" and the architecture addendum is "pending the architect". `grep` finds no FR79 to FR84 in `prd.md`, and `architecture.md:1669,1677` still presents Decisions 13a and 13b (per-type comment tables, fixed widget set) as `[ASSUMPTION]` although Epic 14 supersedes both. Proposed reconciliations are action items below, not applied.

### F5. Review follow-up churn and status lag (accept with process lesson, low)

All nine stories were followed by review-patch commits, from 1 to 5 days after the feature commit (for example 14.1: `ebc16cc` on 10-06, `a6ef9fd` on 10-11). 14.3 and 14.6 had no `bmad-code-review` pass and were still `review` in `sprint-status.yaml` until today, with specs already `done`. Review found real issues each time, so the loop works. The lag is a sync gap, not a defect.

### F6. Duplication map (accept, low)

Four per-type comment route tests are near-identical: `__tests__/api/checklist-comments.route.test.ts` and `logistics-comments.route.test.ts` differ by 2 lines after normalizing names (256 lines each; 1,033 lines across four files). The four per-type route files are 25 lines each over the shared handler, which is the intended design. Duplication is in tests only and could be a single `describe.each`. Offsetting win: the per-type Checklist comment components and tests were deleted in favor of generic ones (`ChecklistCommentSection.tsx` -357, `ChecklistCommentPopover.tsx` -263, `ItemCommentSection.tsx` +358).

### F7. Size growth (accept, no finding)

No god-class emerged. `components/groups/EventLogistics.tsx` grew 747 to 832 lines. `lib/db/queries.ts` shrank 1,843 to 1,716, though it remains a catch-all file. The largest new service is `dashboardWidgetsService.ts` at 357 lines. Source: `wc -l` at HEAD and at `ebc16cc^`.

### F8. Registry-only proof needed a data table (accept)

The epic claims a new widget type can be added through the registry alone "with no schema change". Story 14.9 added the `notes` widget to the registry and renderers, and it did not touch the layout tables, but it did add `event_notes` (migration 041) to store the widget's own data. The claim holds for widget layout and registration; widgets with their own content still need storage. Accepted as-is, recorded so it is not re-flagged.

### F9. Architecture delta and pattern divergence (checked, clean)

New thin-route helpers (`lib/api/itemCommentHandlers.ts`, `lib/api/notesRouteHelpers.ts`) follow one pattern. The live event page now renders the registry-driven dashboard: `components/groups/EventDetail.tsx:323` renders `EventPlanningTab`, which resolves widgets through `widgetRenderers.ts`. This supersedes the earlier memory note that the event-detail route was orphaned (updated alongside this retro).

## Acceptance verdict

**Accepted-with-open-items** (criteria **declared**: `epic-14-context.md` Requirements & Constraints, FR79 to FR84 in the sprint change proposal).

Criteria against evidence:
- Admin chooses widgets and order; per-event layout (FR79, FR80): met in code and tests (14.1, 14.5), unverified against a real database.
- Event type at creation, group default type (FR81, FR82): met (14.7: `CreateEventModal.tsx`, `DefaultEventTypeSetting.tsx`, `AdminGroupSettings.tsx`).
- Editable logistics categories with two behaviors (FR83): met (14.6, reviewed twice).
- Same comment behavior on every item type (FR84): met (14.2 to 14.4, one `item_comments` table and shared handlers).
- 14.1 and 14.2 behavior-preserving: supported by tests only, no runtime check.
- New widget via registry only: met in the stated sense (F8).
- Dinner preset shows no trip wording: met per 14.8 tests.

Why not **accepted**: the criteria are demonstrated only against mocked databases, and finding F1 stands unresolved. Why not **rejected**: all nine stories are `done`, every criterion is met in code, and F1 is a release gate rather than evidence of failure. The epic should not be deployed until action item 1 is done.
