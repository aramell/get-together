## Intent

**Problem:** Of the 5 dashboard widgets, `EventChecklist.tsx`, `EventLogistics.tsx`, and `EventPolls.tsx` already poll their data every 5 seconds (a `pollingIntervalRef` + `isFetchingRef`-guarded `setInterval(fetchX, 5000)` set up in their mount `useEffect` and cleared on unmount), so group members see other members' changes without reloading. `EventTimeline.tsx` and `EventPhotoGrid.tsx` still only fetch once on mount (`EventTimeline.tsx` even has a comment stating "no polling for the Timeline section"), so on the unified dashboard (Story 13.1) two of the five widgets silently go stale while the other three refresh live — an inconsistent, easy-to-miss gap now that all five sit on one continuous page.

**Approach:** Extend the exact same polling pattern already used by `EventChecklist`/`EventLogistics`/`EventPolls` to `EventTimeline.tsx`'s `fetchItems` and `EventPhotoGrid.tsx`'s `fetchPhotos` — same `pollingIntervalRef`/`isFetchingRef` shape, same 5000ms interval, same cleanup-on-unmount, same in-flight-guard behavior (a slow response blocks a stacked overlapping poll, verified the same way the existing widgets' tests already do it: fake timers + `jest.advanceTimersByTime(5000)` asserting the fetch-call count). No new sync mechanism, no change to the 3 already-polling widgets, no change to any API route. Remove `EventTimeline.tsx`'s now-inaccurate "no polling" comment. Add one polling test per widget (mirroring `EventChecklist.test.tsx`'s existing "polls every 5 seconds and does not stack overlapping requests" test) to `EventTimeline.test.tsx` and `EventPhotoGrid.test.tsx`.

</frozen-after-approval>

## Implementation Notes

Extended the existing `pollingIntervalRef`/`isFetchingRef` + `setInterval(fetchX, 5000)` pattern (already used identically by `EventChecklist.tsx`, `EventLogistics.tsx`, `EventPolls.tsx`) to `EventTimeline.tsx`'s `fetchItems` and `EventPhotoGrid.tsx`'s `fetchPhotos` — same shape, same 5000ms interval, same in-flight guard, same cleanup-on-unmount. Removed `EventTimeline.tsx`'s stale "Fetch once on mount/tab-open only — no polling for the Timeline section" comment. No API route changes; no changes to the 3 already-polling widgets.

Replaced each file's existing "does not poll" / one-shot-fetch test with a "polls every 5 seconds and does not stack overlapping requests when a response is slow" test, mirroring `EventChecklist.test.tsx`'s existing polling test exactly (fake timers, `jest.advanceTimersByTime(5000)`, a deliberately-slow second response to prove the in-flight guard blocks a stacked third call). For `EventPhotoGrid.test.tsx`, had to filter the mock `fetch` by URL (`.includes('/photos')`) rather than counting every call — `AuthProvider` issues its own unrelated `fetch('/api/auth/me', ...)` on mount, which a URL-unfiltered counter picked up and inflated the "initial fetch" count to 2. `EventTimeline.test.tsx`'s mock already filtered by `/timeline`, avoiding that issue. Also added `jest.useRealTimers()` to `EventPhotoGrid.test.tsx`'s `afterEach` (missing before; `EventTimeline.test.tsx` already had it).
