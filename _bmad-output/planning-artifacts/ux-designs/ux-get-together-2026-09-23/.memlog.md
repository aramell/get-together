- (decision) Core UX problem: group currently plans via raw email threads (not the app yet); goal is for the app to fully replace that so no one has to scroll a thread to find 'who's in' — not about app-generated notification emails, not about the existing Plan Capture & Import (email-forwarding) feature.
- (event) Sources confirmed: prd.md, epics.md. Extraction: Epic 6 (Comments, FR43-48) and Epic 12 (Event Planning Dashboard — Planning tab: photos/checklists/timeline/logistics/polls) are both fully shipped (all stories done; Epic 6's epic-level 'in-progress' flag looks stale). This is a refinement pass on live functionality, not greenfield design. PRD problem statement frames the pain as fragmented group-text coordination (not email specifically) — user's framing of 'email' is their own group's actual channel. Closest existing journey: Journey 4 (Casey, Casual Member) catching up after time away via push notification.
- (decision) Pain point, in user's words: most planning currently happens in texts/emails outside the app; hard to keep up with who's doing what and what's planned, especially right before the event or during it. Wants a single source of truth for event/trip details plus checklists, planning lists, itineraries — this maps directly onto Epic 12's existing Planning tab (checklists, timeline/agenda, logistics, polls). Open question: is this an adoption/discoverability/simplicity gap in the shipped feature, or a real capability gap (e.g. no dedicated itinerary view, weak pre-event/during-event at-a-glance surface)?
- (decision) Concrete journey beat: mid-trip, need to check 'who's making dinner tonight' — currently means digging through an email/text thread. Vision, in user's words: a DASHBOARD — 'a one-stop shop for all the things you'd need to check for planning as well as checking during the event.' User has not personally used the shipped Epic 12 Planning tab yet, so this is a fresh gut-check of the vision, not a reaction to the existing UI.
- (event) Current Planning tab audit (from code, no live app run): event page has only Details/Planning tabs; Planning is a single vertical scroll of 5 fixed sections (Photos, Checklist, Timeline, Logistics, Polls) — no summary/glance view, no sub-tabs. Checklist and Logistics items have NO date/time field at all — directly explains the user's 'who's making dinner tonight' pain: nothing ties a checklist item to a specific day on a multi-day trip. Liveness is inconsistent: Checklist/Logistics/Polls poll every 5s, Timeline and Photos only fetch once on mount (can go silently stale) — Timeline is the one section with real times and it's the one that doesn't refresh. Public read-only link view (PublicEventPlanning.tsx, very recently shipped) shows only Schedule/Checklist/Who's-Bringing-What, omits Photos/Polls, single fetch no polling.
- (decision) IA decision: dashboard becomes the default landing view when opening an event (replaces the current 'Details' tab as the entry point). It should also have its own direct/bookmarkable link so people can jump straight in without full login+navigation — explicitly for the 'close to the event, need to check something quick, or mid-event' moment. Form factor confirmed: web app only for this pass.
- (decision) No-login quick-access link: audience is 'any group member' (not restricted to organizer/owner, not framed as general public even though mechanism may resemble the existing public token link). Read-only when not logged in. Open: whether logging in from that same link upgrades to interactive (check off items, claim logistics) — plausible continuity, not yet confirmed with user.
- (decision) Customization scope: reorder/hide widgets on the dashboard; one shared layout per group (not per-user) — whoever reorders/hides changes it for everyone in the group.
- (decision) No-login link shows the SAME dashboard content as the logged-in view (mirrors whatever widgets the group has reordered/hidden), rendered read-only — not a separate reduced view. This supersedes the current shipped PublicEventPlanning.tsx behavior (which hardcodes Schedule/Checklist/Logistics only, omitting Photos/Polls). DESIGN.md scope: keep existing Chakra UI look as-is, no visual refresh — this pass is EXPERIENCE.md-led (structure/behavior), DESIGN.md stays minimal/inherited.
- (decision) Confirmed in scope: (1) add optional date/day-of-trip to Checklist and Logistics items, enabling a 'today' grouping/filter on the dashboard — directly closes the 'who's making dinner tonight' gap. (2) All dashboard widgets (including Timeline and Photos, which currently only fetch once) become live/consistently refreshing, matching Checklist/Logistics/Polls' existing pattern — nothing should go stale during an event.
- (decision) IA closure: current Details content (event name/date/location, RSVP status badge, Comments) becomes the header/top section of the new Dashboard, not a separate tab — Dashboard fully replaces the old Details+Planning tab split. Protagonist for Key Flows: Andrew.

- (decision) New scope, added after seeing the mocks: per-item comments on Checklist items, Logistics items (Bring List/Carpool), Timeline items, AND Polls — same treatment across all four. Interaction: hover/focus shows a lightweight popover preview of existing comments; click opens a small modal with the full comment thread (view + add). Plus a general/trip-level comment surface remains accessible from the Dashboard (this is the existing Epic 6 event-level comment feature, not new). Capability gap: today Comments (Epic 6, FR43-48) only attach to events and wishlist items — Checklist/Logistics/Timeline items and Polls are not commentable entities in the current data model, so this requires new entity support, same category of gap as the earlier date/time addition.
